Ты работаешь над DaiBed — BedWars-подобной воксельной PvP-игрой на C++17 и
raylib 5.0. Прочитай `docs/VISION.md` (философия проекта, нарушать нельзя) и
`docs/ROADMAP.md` (план) перед началом работы.

## Контекст проекта

- **Жанр:** геройский BedWars. Команды защищают свой EnergyCore (аналог
  кровати), добывают ресурсы, закупаются в магазине, строят и ломают блоки,
  уничтожают чужие коры. Падение в воид смертельно — это часть дизайна.
- **Герои:** 6 героев (Радон, Орбита, Бром, Конвой, Лихо, Свидетель) с
  пассивкой и активными способностями; каждый воплощает один из стилей игры
  BedWars. Реализация — data-driven в `HeroSystem`, без if/else по героям в
  общем коде.
- **Эталон ощущений:** Minecraft. Движение, постановка блоков, тайминги боя
  должны переноситься мышечной памятью Minecraft-игрока.
- **Будущее:** настоящий сетевой мультиплеер (authoritative server).
  Поэтому: симуляция отделяется от рендера, никакой логики правил в
  Renderer/UI, никаких глобальных синглтонов, детерминизм важен.

## Структура кода

- `src/Game.cpp/.h` — оркестратор (пока монолит ~8К строк: симуляция+клиент)
- `src/GameBotAI.cpp`, `src/BotAI.h` — ИИ ботов (стратегия → роль → интент,
  utility-скоринг); тюнинг через `BotTuningGenome` (JSON)
- `src/World/Player/Team/Core/Generator/Shop/CombatSystem` — игровые системы
- `src/HeroSystem.*`, `src/Hero.*` — герои и способности
- `src/GameRules.cpp` — условия победы
- `src/Renderer.cpp`, `src/GameUI.cpp` — только презентация
- `src/Network/` — интерфейсы Client/Server + LocalNetworkMock (сети ещё нет)

## Сборка и проверка

```bash
cmake -S . -B build && cmake --build build -j$(nproc)
# Headless-прогон ботовых матчей (главный регрессионный тест):
./build/DaiBed --automatch --runs 4 --speed 32 --minutes 20
# Результаты: automatch_stats.json (winrate, длительность, причины конца)
```

Требования к любому изменению:
1. Проект собирается без новых предупреждений.
2. Automatch: матчи завершаются победой (не таймаутом), длительность в
   разумном коридоре, winrate команд без аномалий. Сравни stats до/после.
3. Не ломай существующие правила игры. Если задача требует изменить
   правило — остановись и опиши предложение, не реализуя.
4. Стиль: как в окружающем коде (C++17, 4 пробела, фигурные скобки на новой
   строке, имена `camelCase_` для полей). Русские строки в UI — норма.
5. Никакого raylib в файлах игровой логики, если задача про симуляцию.

## Бэклог (выбери одну задачу)

**T1. Активная ранняя игра ботов.** Сейчас все боты первые 1-2 минуты стоят
у своего кора: в `FindBestResourcePlanForBot` (GameBotAI.cpp) цель
выбирается по квадрату дистанции, и домашние пикапы всегда выигрывают у
нейтральных генераторов (бонусы 180-420 против штрафа дистанции 900+).
Сделай: у домашнего генератора остаётся максимум один бот (роль Collector
в приоритете), остальные с первых секунд получают цели — нейтральные
генераторы или мост к миду. Критерий: в automatch-прогоне в первые 60
секунд ≥ половина каждой команды покидает радиус 12 блоков от своего кора;
winrate и завершаемость матчей не деградируют.

**T2. Выделение MatchSimulation (Фаза 0.1, делать по шагам).** Перенеси
владение World/Player/Team/Core/Generator/Shop и тик симуляции из Game в
новый класс `MatchSimulation` без включений raylib (математику векторов
заменить своей или raymath-копией). Game получает ссылку и рендерит. Шаг
можно ограничить: сначала только `UpdatePassiveRegeneration`,
`UpdateBaseHealing`, `GameRules` и генераторы. Критерий: сборка чистая,
automatch идентичен по статистике до/после.

**T3. PlayerCommand (Фаза 0.3).** Введи структуру `PlayerCommand` со всеми
действиями игрока за тик; локальный ввод и боты формируют её, симуляция
потребляет. Критерий: поведение в automatch не изменилось; ни одно
обращение к `currentInput_` не осталось внутри кода, который двигает
игроков или применяет действия.

**T4. Minecraft-feel аудит движения.** Сведи в документации релиза таблицу
текущих констант (скорость ходьбы/спринта/шифта, прыжок, гравитация,
досягаемость, KB) против эталонных значений Minecraft Java (источник —
вики). Подгони очевидные расхождения (>15%) под эталон, спорные — only
задокументируй. Критерий: таблица в docs, изменённые константы перечислены
в коммите, automatch не деградирует.

**T5. Death/respawn UX.** Экран смерти: кто убил, чем, сколько ждать
респауна; final death — отдельный экран. Только GameUI/Renderer, логику не
трогать. Критерий: вручную убедиться через обычный запуск игры.
